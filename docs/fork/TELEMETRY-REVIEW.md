# Upstream telemetry inventory and proposed containment

Audit date: 2026-11-04. Read-only source review of the iOS fork at commit [`f295948ad9ba8fb1cb668dc0b645c486d1f2ec74`](https://github.com/Livara-Dev/Telegram-iOS/commit/f295948ad9ba8fb1cb668dc0b645c486d1f2ec74). Paths below are relative to that checkout; line references identify this revision. No application source, workflow, or test was changed during this audit. This report extends the [security assessment](../SECURITY_ASSESSMENT.md) and [architecture review](IOS-ARCHITECTURE.md); it does **not** establish a telemetry-free binary, a passed test, or runtime absence of disclosure.

## Main findings

The fork build configuration (`tools/fork_baseline/baseline.py:57–80`) sets `org.livara.ayugram`, `app_center_id="0"`, `is_internal_build="false"`, and `is_appstore_build="false"`. Those values do not disable Telegram's own analytics and diagnostic RPCs. In addition to the already documented app logs/network telemetry/call logs, this revision automatically reports channel reading metrics and music listening durations.

AppCenter is excluded from this bundle's declared dependency graph, but **the string `"0"` is not a valid off switch**: the startup condition checks only nonempty ID and non-App-Store build. The independent bundle-ID allowlist currently prevents the SDK from linking. Use an empty ID and remove the optional startup/dependency path as defense in depth if permanently excluding AppCenter.

Most observed automatic reports go to Telegram through the existing authenticated MTProto API, not a new developer-controlled HTTP endpoint. That distinction does not satisfy the requested no-telemetry policy: Telegram can associate authenticated reports with an account. Do not adopt upstream comments describing payloads as anonymous as an anonymity guarantee.

## Related local and user-requested diagnostic paths

- `TelegramCore/Sources/Utils/Log.swift:47–68,108–112,216,399` wires API, Postbox and network short logs. `shortLog` does not check `logToFile`, `logToConsole` or `redactSensitiveData` before writing the supplied text. `AppDelegate.swift:713–717` disabling ordinary release-file logging therefore does not disable short-log storage. Redaction relies on producers and is not proven here. Because the logger is shared, the soft-reset upload is also an account-isolation concern: it does not select only logs belonging to the uploading account. No evidence found that archive payloads are currently logged, but canary tests are needed.
- `CrashReporting/Sources/CrashReportCollector.swift` registers MetricKit and persists crash diagnostics locally. `AppDelegate.swift:356` starts it without an internal-build gate. No network client was found inside the `CrashReporting` module. `is_internal_build=false` disables the default **prompt**, not collection (`CrashReporting/Sources/CrashReport.swift:116`; `DebugSettingsUI/Sources/CrashReportsController.swift:450`). Apple OS diagnostics/sharing preferences are outside this source-level conclusion.
- `DebugSettingsUI/Sources/CrashReportsController.swift:23,216–315,450–478` can send a selected crash archive through Telegram to hardcoded username `iOSCrashReportsBot`. The detailed-view route confirms; the startup prompt's Send action goes directly to send. Prompts default off in this fork, but a saved `showCrashReportAlerts` override can enable them and Debug Settings remains a user-accessible route. This is user-triggered remote diagnostics, not automatic MetricKit HTTP upload. To promise a local-only diagnostics product, remove/hide the bot route and preserve local view/delete, or design explicit destination-aware export separately.
- `TelegramCallsUI/Sources/CallRatingController.swift:13–40` sends ratings through `phone.setCallRating`; with `includeLogs` it also sends a log as a normal message to hardcoded Telegram peer 4244000; with nonempty comment it sends that text there. `CallFeedbackController.swift:216` defaults **includeLogs=true**. The user submits feedback, but default attached diagnostics must not be mistaken for explicitly enabled telemetry. Set default false / remove attachment and hardcoded support-message route according to the intended local-only policy; preserve intentional rating submission separately if retained.
- `AppDelegate.swift:3251–3306` has an HTTP development-update check gated by internal build or saved `enableUpdates`, and a configured URL. Internal builds are false but saved override still matters. This is an updater rather than analytics; it needs endpoint policy review before a release.
- `AppDelegate.swift:1843–1983` contains a legacy background-upload callback targeting localhost, plus an example.com background-download function whose call is commented out. The upload callback is supplied through `SharedAccountContext` and `TelegramAccountAuxiliaryMethods`, but repository search found no actual invocation of the stored `AccountAuxiliaryMethods.backgroundUpload` property. Treat as dormant/unverified, not proof of live exfiltration. Removing dormant sample endpoints is a separate cleanup; do not alter the real MTProto media uploader to accomplish it.

## Scope boundaries to preserve

Do not remove or blanket-filter `Network.request`, MTProto engines, auth keys, retry policies, protocol acknowledgements, message updates, media upload/download, call signaling, APNs or reCAPTCHA. `Authorization.swift:132–135` uses `auth.requestFirebaseSms` for Telegram's authentication challenge; this name is not proof of Firebase Analytics. The linked RecaptchaEnterprise challenge path (`AppDelegate.swift:45,~625–685`) is an authentication/anti-abuse dependency and needs its own policy/dependency review, not blind removal.

Likewise, `messages.reportMessagesDelivery`, ordinary read state, story receipts, spam reports and user-requested channel statistics are product/protocol behavior, not interchangeable with optional diagnostics. `AdMessages.swift:593,696,705` sends sponsored-message view/click accounting: inventory it as behavior measurement, but classify it separately against Telegram's sponsored-message API requirements before changing it. The requested Ghost behavior already has documented API-policy conflicts. This audit does not certify the app as having no other third-party connections (web content, maps, payments, bots, media providers or OS services remain separate surfaces).

## Smallest safe actionable diff

Implement as a separate privacy commit with explicit tests; do not mix this into archive capture, filtering or a broad network rewrite.

1. **Contain optional RPC sinks first.** Disable the generic app-event producer overloads and sync-trigger helper; make the app-log worker discard only legacy tag-18 records for root peer 0 in its own Postbox without making requests. `Postbox.swift:833` provides `operationLogRemoveAllEntries(peerId:tag:)`; if using incremental cleanup, bound batches and keep it off the main thread. Leave all other operation tags/peers and canonical data untouched. Removing only its `AccountTaskManager` start leaves stale data; disabling only new insertion leaves old uploads active.
2. Remove the soft-auth-reset diagnostic sender/callback in `Account.swift`, while preserving the network's actual auth handling. Disable both `RateCall.swift` debug-log sinks **before** file reads/compression/multipart work. Return completion, not fabricated server success or a forever-pending signal; `phone.setCallRating` is a separate explicit action. Also contain `reportPeerReadMetrics` and `reportMusicListened` at their specific engine facades. These are distinct outgoing paths and can complete without changing canonical messages or playback.
3. **Stop production collection/timers.** Make production `networkTelemetryShouldRecord` return false regardless of DEBUG, server configuration or mutable test override, and stop the account reporter. Directly instantiated recorder/formatter unit tests can remain; they should not be a runtime opt-in. Existing initializer's disabled branch already schedules cleanup of `network-telemetry` for primary non-extension networks; test exact path and avoid deleting unrelated account content. Prevent `ChatHistoryListNode` from creating the viewport tracker and `MediaManager` from creating the music tracker. Central sink guards still protect old deinit/pending callbacks and future callers. Stop unnecessary download-stat aggregation without changing local network-usage counters. This avoids continuing unwanted local collection/battery use after transport containment.
4. Set `app_center_id` to empty and permanently remove AppCenter startup/optional dependency selection if no AppCenter build will be supported. Do not add a mutable or server-controlled "privacy off" path. Review persistent legacy overrides for optional diagnostic prompts; defaults alone do not change an existing user's settings.
5. Treat local short-log retention and user-directed crash/call-feedback export as an explicit separate decision. Under the current requested local-only/no-telemetry intent, remove hardcoded diagnostic-send routes and keep safe local view/delete controls. If manual exports are later wanted, show destination/content and require a fresh action; do not silently attach logs by default. This step is needed before a stronger local-only diagnostics claim, even after automatic sinks are contained.

This plan changes optional producers and typed diagnostics entry points rather than filtering generic MTProto traffic. Source code for serializers and recorder tests may remain; presence of a type alone is not evidence it runs. A source guard should allow such definitions/tests while failing new production invocations of forbidden diagnostic sinks.

## Necessary evidence

- **Real Postbox regression:** seed old add/sync operations, malformed/unknown telemetry operations, another operation tag and canonical messages; run disabled worker; verify no request emitter is called, only intended telemetry records are removed, producers create no new records, and reopen/account B stay isolated. Test re-entry, cancel/restart and more than one cleanup batch if batching.
- **Remote flag and build matrix:** boolean/numeric/string enable flags, DEBUG/release, fresh and legacy preferences, unauthorized/authorized, primary/supplementary/extension. Production factory must not instantiate telemetry even with test override set; direct low-level formatter tests need not imply production enablement. Existing `NetworkTelemetryTests.swift:1138–1182` currently expects enabled recording and must be updated deliberately, not ignored or removed wholesale.
- **Typed sink tests:** injected request/file-operation counters prove app log, soft-reset log, call debug/full log, read metrics and music reports do not call their RPCs or multipart uploader. Preserve explicit completion contracts; verify call-stop cleanup, playback control/local counters and auth state behavior separately. Tests against a stand-alone policy Boolean alone are insufficient.
- **UI/lifecycle checks:** broadcast chat scroll/close including filtered placeholders; music switch/close/pause; call stop with both debug flags and full-log server response; account switch; remote reconfiguration; crash prompt legacy override and call-feedback defaults. Do not create reports during node deinit or replay pending submissions after restart.
- **Runtime release check:** build the exact latest revision, inspect linked frameworks/binary for AppCenter and other unexpected SDKs, then run synthetic accounts with archive/log canaries while instrumenting outgoing typed request methods and network destinations. Packet captures alone cannot identify encrypted MTProto method payloads; combine endpoint observation with request-boundary instrumentation. Confirm no auth/session/archive canaries enter logs or diagnostic payloads. Verify normal login, reconnect, send/receive, uploads, downloads, calls and read-state behavior still work.
- **Honest status:** none of these proposed changes/tests was executed by this audit. Current source is not telemetry-free. Even a passed diagnostics test suite would not prove that web views, OS telemetry or every external integration has no network behavior.
